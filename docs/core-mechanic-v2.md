# ダラリカ中心メカニクス v2

## 一文でいうと

> **休まず次の行動へ流れそうな境目を、いったん自分で選び直せる場所へ戻し、頭に引っかかった用事を未来へ預けて、休養状態へ戻る。**

ダラリカは「休み方をたくさん提案するアプリ」より、**次へ流れる慣性を一度ほどく装置**として設計する。

## 旧MVPで分かったこと

PR #4 の最小MVPは、

> Start → Recovery Check-in → Recovery Menu → Recovery Session → Thought Parking → Reflection

を一周できる基準点を作った。

この形で分かった問題は、最も難しい判断である「休もう」「ダラリカを開こう」をユーザー側ですでに済ませてもらっていること。

また、中心が Recovery Menu と countdown timer に見えるため、そのまま改善すると既存の休憩・mindfulness系アプリへ寄りやすい。

## v2の中心ループ

```text
[Boundary Gate]
   ├─ このまま続ける → 介入終了
   ├─ いったん止まる
   │      ↓
   │   [Unwind]
   │      ↓ 1 tap
   │   [Rest Mode]
   │      ├─ 思いついた → [Thought Parking] → [Rest Mode]
   │      └─ ここまでにする → 終了
   │
   └─ 思いつきだけ預ける
          ↓
      [Thought Parking]
          ↓
      [Rest Mode]
```

## 1. Boundary Gate

### 役割

休養を始める画面ではなく、**自動的な継続を選択へ戻す画面**。

ユーザーに「休むべき」と言わない。

選択肢:

- いったん止まる
- 思いつきだけ預ける
- このまま続ける

「このまま続ける」を正規の選択肢として置くことで、介入を禁止・罰にしない。

### MVPでの制約

Web prototype は、他アプリを開こうとした瞬間を検知できない。

したがって v2 では **Boundary Gateを手動で起動する**。ここで検証するのは自動検知ではなく、境目にこの選択肢が現れたときの体験。

2026-09-13 の product viability 再調査により、trigger layer は単なる将来機能ではなく、**価値成立を検証すべき中心仮説の片翼**へ位置づけを変更する。

現Web prototypeでは引き続き手動起動だが、次段では「必要な境目に自然に呼び出されることで、使う必然が生まれるか」を検証する。

候補:

- iOS / Android Shortcut
- browser extension
- OS automation
- URL / home-screen shortcut
- timer / schedule based intervention

## 2. Unwind

### 役割

「あなたは何疲労ですか」と分類するのではなく、**いま何を減らしたいか**を答えるだけにする。

選択肢:

- 考えること
- 身体を使うこと
- 画面や音の刺激
- わからない。とにかく止まりたい

ここではスコア化、原因推定、診断をしない。

選択後に Recovery Menu を挟まず、そのまま Rest Modeへ入る。

## 3. Rest Mode

### 役割

「タイマーを完了する場所」ではなく、**次の行動を決めなくてよい状態**。

基本:

- 大きな countdown を置かない
- 5分程度の目安は内部で持つ
- 時間が過ぎても作業再開を促さない
- 静かな視覚変化だけを置く
- 視覚変化へ呼吸や操作を合わせる必要はない
- 途中終了を失敗扱いしない

Unwindの選択によって、表示する短い言葉だけを変える。

例:

- 考えること → 「答えを出さない時間にする。」
- 身体を使うこと → 「身体をどこかに預けていい。」
- 刺激 → 「情報を増やさない。」
- わからない → 「理由を決めなくていい。」
- Parking直後 → 「預けた。いまはやらなくていい。」

## 4. Thought Parking

### 役割

メモ帳ではなく、**休養から仕事へ飛び出しそうになった瞬間の避難口**。

ルール:

- 一行だけ
- 保存後に一覧を見せない
- 期限、優先度、完了チェックを置かない
- 外部アプリを開く導線を置かない
- 保存後は自動的に Rest Modeへ戻す
- 「忘れないから、今やらなくてよい」を短く返す

Boundary Gateから直接 Thought Parkingへ入れる。

これにより、

> 「返信だけしてから休む」

のような引っかかりを、

> 「返信することだけ預けて、いまは止まる」

へ変換できるかを見る。

## 5. Reflectionを外す理由

旧MVPではセッション後に、

- 少し休めた
- 変わらない
- 途中でやめた

を任意記録していた。

v2では外す。

理由:

- Rest Mode直後に評価行動を要求すると、休養を成果測定へ戻しやすい
- 中心メカニクスの検証に必須ではない
- 「休めたか」を採点するより、「次へ自動的に流れず選び直せたか」を先に見るべき

必要なら後で研究用の任意ログとして再導入する。

## 6. 成功条件

v2の最初の観察点は次。

1. Boundary Gate の「このまま続ける」を含む3択が、押しつけではなく選び直しとして感じられるか。
2. Unwind は状態診断より軽いか。
3. Recovery Menuをなくしても、Rest Modeへ入ることに不安がないか。
4. countdownを主役から外した方が休養らしいか、それとも時間の見通しがなく不安か。
5. Thought Parking後、他の作業へ移らずRest Modeへ戻れるか。
6. 「思いつきだけ預ける → Rest Mode」の直通経路が実際に使いたくなるか。

## 7. 現段階で保留する論点

### trigger layer

2026-09-13 の再調査で、**Standalone Web Appの手動起動だけでは継続利用理由が弱い**と判断した。

ダラリカはstreak、育成、daily content、詳細な履歴分析を意図的に持たない。その思想を維持するなら、ユーザーに毎回「休もう」「ダラリカを開こう」と思い出してもらうのではなく、必要な境目へダラリカ側から現れる仕組みを検証する必要がある。

ただし、高頻度の一律な摩擦はhabituation / attritionを招く可能性があるため、介入頻度を本人が制御できることを前提にする。

次段の候補:

- user-defined apps / sites
- work session終了時
- 夜間の限定時間帯
- browser上の限定trigger
- desktop shortcut / hotkey

詳細: [`research/product-viability-retention.md`](research/product-viability-retention.md)

### Parkingの後処理 — Return Window

Thought Parkingをblack holeにしないため、後から内容を返す仕組みを価値成立に必要な要素として扱う。

ただし、休養中・保存直後・Rest Mode終了直後には一覧を見せない。

基本方針:

1. Rest中は一行だけ預ける
2. その場では内容を隠し、Rest Modeへ戻す
3. 後刻の **Return Window** でまとめて返す
4. Return Windowで「残す / 外部へ送る / 捨てる」を選べるようにする

候補は、1日1回のquiet digest、翌日の最初の能動利用時、次のwork-start trigger、明示的なParking Inbox。

Parking入力時に毎回due dateやreview時刻を聞くことはしない。

### Rest Modeの時間

5分を暫定目安にするが、固定時間に意味があるとはまだ判断しない。将来、時間なし / 3分 / 10分等を比較してよい。
